### 14:01 AIPT local LLM 아키텍처 확인 및 engine Gateway 캐싱 기능 구현
<!-- conversation-to-obsidian:start:slack:C0ACDPUAKN3:20260901_140116_a1702705:2026-09-01 -->
- Channel: slack DM
- Source: session 20260901_140116_a1702705

#### Summary
- AIPT의 local LLM 서빙 엔진은 ollama가 아니라 llama.cpp(ghcr.io/ggml-org/llama.cpp:server)이며, local-llm 컨테이너는 net-backend 전용으로 gateway를 통해서만 도달 가능함을 코드 근거로 확인
- 기존 Network Gateway(L3, tc netem)와 local_llm 백엔드 내부에 인프로세스 훅으로만 존재하던 'engine Gateway'(L7)의 구조적 차이를 설명, web→Gateway(지연)→Gateway(LLM분산)→local llm 4단 토폴로지가 기존엔 미구현 상태였음을 확인
- local-llm은 1대 고정 유지, engine Gateway를 실제 네트워크 리스너(HTTP 리버스 프록시, sidecar, 신규 포트 40079)로 승격시켜 캐싱 로직을 수행하는 방향으로 요구사항 구체화
- 스트리밍(SSE) 요청은 패스스루만 하고 캐싱 미수행 결정 — 요청 시점 단일 분기 + 코드 경로 물리적 분리로 오작동 방지
- 구현: aipt/core/cache_protocol.py(leaf-hash 기반 요청 중복제거 캐싱, SHA-256), docker/engine_gateway.py(L7 리버스 프록시, X-AIPT-Cache 헤더, 캐시미스 시 409), Gateway.send()에 캐싱+자동 재전송+cache_bytes_saved 반영
- 웹 UI 캐싱 on/off 옵션 추가, turns.csv에 cache_bytes_saved 컬럼 추가, 실스택 검증 86.3% wire bytes 절감 확인, 기존 pytest 547개 회귀 없음 확인 후 커밋(2c473fd8) 및 push 완료

#### Decisions
- local-llm 서버 인스턴스는 1대만 유지하고 다중 분산은 하지 않는다
- engine Gateway는 local-llm 컨테이너와 같은 배치(sidecar 프로세스)로, HTTP 리버스 프록시 방식(OpenAI 호환 API 그대로 통과)으로 구축한다
- 이번 세션 내에서 리스너 승격 + 실제 캐싱 로직(leaf-hash 방식)까지 이어서 구현·완료
- 스트리밍(stream=true) 요청은 캐싱을 적용하지 않고 순수 패스스루로 처리, 요청 시작 시점에 한 번 판단하고 코드 경로를 물리적으로 분리한다
- 검증은 docker-compose 실제 스택 기동 후 curl/pcap/웹 API 경로로 end-to-end 확인하는 방식을 우선한다
- ARCHITECTURE.md/DESIGN.md는 동시 진행 중이던 다른 세션이 이미 커밋해둔 상태라, 이번 세션은 코드 변경분만 좁게 git add하여 별도 커밋 후 push
