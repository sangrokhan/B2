### 14:56 TCP RTO SRTT/RTTVAR 코드 분석
<!-- conversation-to-obsidian:start:slack:C0ACDPUAKN3:20260825_145615_d7a31b11:2026-08-25 -->
- Channel: slack DM
- Source: session 20260825_145615_d7a31b11

#### Summary
- Linux 커널 RTO 계산 코드(tcp_rtt_estimator, __tcp_set_rto)를 직접 분석해 RFC 6298와의 차이 규명
- RTO 최종식은 `(srtt_us>>3) + rttvar_us`로, RFC의 K=4 곱셈이 명시적으로 보이지 않음 — mdev를 4배 스케일로 저장해 rttvar_us에 이미 흡수시킨 설계임을 확인
- SRTT는 실제값×8로 저장되는 fixed-point 방식(정수 시프트만으로 EWMA 구현), RTTVAR는 RFC처럼 매 샘플 지수평활이 아니라 "1 RTT 구간 내 최대 편차(mdev_max)"를 사용
- RTT 감소 시(m<0) mdev 갱신 gain을 추가로 축소하는 비대칭 처리(Eifel 변형)가 있어 RTO가 너무 빨리 줄어드는 것을 방지함을 확인

### 17:59 TCP ssthresh 값 설정 원인 분석
<!-- conversation-to-obsidian:start:slack:C0ACDPUAKN3:20260825_175909_f42b60c9:2026-08-25 -->
- Channel: slack DM
- Source: session 20260825_175909_f42b60c9

#### Summary
- ssthresh가 무한대(TCP_INFINITE_SSTHRESH)에서 특정 값으로 바뀌는 3가지 커널 진입점 정리: tcp_enter_loss(RTO), tcp_enter_recovery(Fast Retransmit), tcp_enter_cwr(ECN CE)
- "손실이 관측되지 않았는데 ssthresh가 내려간" 경우의 3가지 실제 원인 규명: ① ECN CE 마킹(진짜 드롭 없음), ② Spurious RTO(지연이지 손실 아님, RTO 타이머 만료만으로 tcp_enter_loss 호출됨), ③ RACK 기반 reordering 오판
- 연구 주제와 직결: idle 후 RTTVAR가 stale한 상태에서 idle 직후 첫 요청이 cold path(캐시 미스/TLS 재개/GPU inference 지연 등)를 타 RTT가 급증하면, 드롭 없이 RTO가 먼저 만료되어 ssthresh가 내려가는 시나리오가 유력한 후보로 지목됨
- cwnd_restart(RFC 2861/CWV)는 ssthresh와 무관한 별개 메커니즘임을 확인 (혼동 주의 포인트로 정리)
- 판별 절차 제시: nstat -az로 TCPTimeouts/TCPSpuriousRTOs/TCPLossUndo/TCPECNRcvd 확인, ss -ti로 retrans/lost/ssthresh 동시 확인

#### Decisions
- pcap에서 재전송 세그먼트가 안 보이면서 ssthresh만 내려간 케이스는 idle-gap 랩의 idle 후 RTT 급증에 의한 spurious RTO가 가장 유력한 설명으로 판단, ECN CE 비트와 nstat의 TCPSpuriousRTOs 두 지표를 우선 확인하는 방향으로 정리
